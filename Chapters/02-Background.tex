\section{Observability and Operational Telemetry}
\label{sec:background:observability}

Observability concerns the extent to which a system's internal behaviour can
be understood through the information it exposes. In distributed software,
this information includes operational telemetry such as logs, metrics and
traces. Monitoring uses such information to track selected aspects of system
behaviour, while observability supports investigation of the conditions
behind that behaviour \parencite{usman2022observability}. These activities
are closely related. For example, an alert about an increased error rate
identifies a condition requiring attention. Explaining the increase requires
evidence about the affected requests and components.

\noindent\textbf{Logs.} A log records events emitted by an application or
another system component. Log entries commonly include timestamps and
messages describing what occurred. A log entry can provide details about a failed operation, but
it is not necessarily associated with a particular user request. Additional
context is needed to connect that event to activity elsewhere in the system
\parencite{opentelemetry2026observability}. This distinction matters when
several requests are processed concurrently: observing an error during an
incident does not, by itself, establish which request it concerns.

\noindent\textbf{Metrics.} Numerical measurements describe system behaviour
over time, such as resource utilisation, request rates and response times.
They support
identification of changes in behaviour and the definition of alert conditions
\parencite{usman2022observability}. Metrics can summarise many observations.
For example, an error rate describes the proportion of unsuccessful requests
over a time interval. That summary can indicate the scale of a problem, while
further information is needed to explain an individual failure.

\noindent\textbf{Distributed traces.} A distributed trace links the recorded
steps involved in handling a request. It is made up of \emph{spans}, each
describing one operation and its timing. For example, a request to a web
application may lead to a database query. That query can be recorded as a
span within the request's trace
\parencite{opentelemetry2026observability}. Linking these spans helps show
which operations belong to the request and where time was spent
\parencite{ashok2024traceweaver}.

To connect operations across services, the services need to pass tracing
information between them. The W3C Trace Context standard defines a common
format for this information, including an identifier for the trace
\parencite{w3c2021tracecontext}.

A trace may still have gaps. If a component is not set up to record tracing
data, its operations may be missing from the trace
\parencite{ashok2024traceweaver}. A missing span therefore does not prove
that the request never reached that component.

The complementary roles of these signals can be illustrated by a hypothetical
application failure. A metric might show an increase in unsuccessful
requests during a particular interval. A trace of one failed request might
identify an unsuccessful database operation, while a log associated with
that operation might record an authentication rejection. The metric
describes a broader change in service behaviour. The linked trace and log
provide evidence about an individual failure. This evidence supports
investigating the authentication rejection, but further information is
needed to explain why it occurred. The rejection alone does not establish
malicious activity or show that other failed requests have the same cause.

Interpreting these observations also requires attention to dependencies.
Research on microservice diagnosis shows how performance problems can
propagate between dependent components, so the location where a symptom is
observed may differ from the origin of the problem
\parencite{gan2021sage}. Correlation helps establish which observations
belong to the same activity, while diagnosis requires assessing what those
observations imply about the failure.

Telemetry can also provide the basis for derived features used in analysis.
In the hypothetical example, a count of recorded authentication rejections
for a service within a defined interval could be calculated from its logs.
This summary describes a pattern across events whose relevance depends on
the problem being investigated. Research on machine learning in security
shows how models can exploit incidental patterns unrelated to their
intended task \parencite{arp2022dosdonts}. This motivates examining the
meaning and diagnostic relevance of telemetry and derived features alongside
their availability and correlation across systems.


\section{The Cloudflare-to-Azure Request Path}
\label{sec:background:request-path}

The Norlys use case describes a request path through Cloudflare, Azure
Firewall, Azure infrastructure and the application
\parencite[Background]{norlys_operations_agents}. These layers perform
different tasks and provide different views of a failure.

\noindent\textbf{Cloudflare.} For a hostname with proxying enabled,
Cloudflare receives web traffic on behalf of the \emph{origin server},
which hosts the website or application. This allows Cloudflare to apply
services such as security filtering and caching
\parencite{cloudflare2026proxy}. Its web application firewall (WAF) checks
incoming web and API requests against rules. These rules can use request
properties such as the URL path, headers and body content. Cloudflare
Security Events provides information about requests that matched security
rules \parencite{cloudflare2026waf}. This evidence can help an investigation
determine whether a security rule affected a request before it reached
the application.

\noindent\textbf{Azure Firewall.} Azure Firewall controls traffic through
configured rules. The rules it evaluates depend on their type and the
direction of the connection. For example, application rules are used for
supported outbound traffic and are not applied to inbound connections
\parencite{microsoft2026firewallrules}. Its logs can record source and
destination addresses, port numbers, protocols and whether traffic was
allowed or denied. These fields help describe the connection and the
firewall's decision \parencite{microsoft2026firewallmonitor}. A denied
connection shows that traffic was blocked. Further evidence is needed to
decide whether the block was intended or caused by a configuration error.

\noindent\textbf{Azure infrastructure.} Here, infrastructure refers to the
resources that host the application and route traffic to it. Azure exposes
several types of telemetry about these resources. Platform metrics describe
resource behaviour over time, while resource logs describe operations
within a resource. The Azure activity log records subscription-level
events, including configuration changes
\parencite{microsoft2026monitordata}. These sources help distinguish a
problem with the hosting environment from an error recorded by the
application. The available metrics and logs depend on the resource type
and its monitoring configuration.

\noindent\textbf{The application.} Application telemetry provides evidence
about the processing of a request. When enabled, Application Insights can
collect information about application requests, exceptions and calls to
dependencies \parencite{microsoft2026monitordata}. A dependency is another
component that the application uses, such as a database or an external
service. This information can help explain why a request failed after it
reached the application.

The difference between these views can be illustrated by a hypothetical
request that reaches the application but fails while waiting for a database
response. A firewall log might show an allowed connection, while application
telemetry records the database timeout. Allowing the connection does not
mean that the application completed the request successfully. The records
must also be linked to the same activity before they can support a common
explanation. This is consistent with research showing that problems can
affect several dependent components
\parencite{gan2021sage}. The purpose of examining the request path is to
connect these observations and identify where further investigation is
needed.


\section{Telemetry Correlation Across Systems}
\label{sec:background:correlation}

Telemetry correlation connects observations that describe the same request
or related operations. Knowing that two services communicate is not enough
to link their individual requests. Several requests can pass through the
same services at the same time, making their records difficult to separate
\parencite{ashok2024traceweaver}.

\noindent\textbf{Shared identifiers.} An identifier carried between services
provides an explicit link between their observations. The W3C
\texttt{traceparent} header carries a trace identifier and an identifier
for the calling operation. These fields allow participating services to
maintain the connection between operations within a trace
\parencite{w3c2021tracecontext}. The OpenTelemetry log data model also
defines optional \texttt{TraceId} and \texttt{SpanId} fields. When recorded,
they associate a log entry with a trace and a particular operation
\parencite{opentelemetry2026logsmodel}. For example, an application error
log containing these fields can be linked to the operation that produced it.

Identifiers also need to be understood in the context of the system that
creates them. Cloudflare assigns a Ray ID to requests and passes it to the
origin server in the \texttt{cf-ray} header. If the origin records this
header, it provides a way to relate its logs to Cloudflare records.
However, Cloudflare states that Ray IDs are not guaranteed to be unique
for every request \parencite{cloudflare2026rayid}. A matching Ray ID
therefore needs to be considered alongside other request details.

\noindent\textbf{Timestamps.} Time information helps narrow an investigation
to a relevant interval, but the meaning of a timestamp matters.
OpenTelemetry distinguishes \texttt{Timestamp}, the time of the event
according to the source clock, from \texttt{ObservedTimestamp}, the time
when the collection system observed it
\parencite{opentelemetry2026logsmodel}. These values can differ, so comparing
event time in one source with collection time in another can give a
misleading view of when the events occurred.

Clocks on different machines can also disagree. This is commonly called
\emph{clock skew}. Documentation for the Jaeger tracing system describes how this can
make an operation appear to begin before the operation that called it
\parencite{jaeger2025clockskew}. Timestamp order alone therefore does not
always establish the actual order of events.

\noindent\textbf{Correlation without shared identifiers.} When no common
identifier is recorded, relationships can be inferred from other evidence.
Research on trace reconstruction combines request timings with knowledge
of which services call one another to identify likely relationships
\parencite{ashok2024traceweaver}. This is different from reading an explicit
link recorded during request processing. Consider two requests reaching the
same service within the same second. A service name and a timestamp rounded
to that second would fit both requests. Choosing one would require more
evidence. An inferred match should therefore be distinguished from a link
supported by recorded identifiers.

\noindent\textbf{Incomplete evidence.} Correlation also depends on which
records are available. For example, Cloudflare Security Events can use
sampled data, meaning that a search may not include every event
\parencite{cloudflare2026rayid}. A missing result in such a search does not
prove that the request never reached Cloudflare. Together, these examples
show why an investigation needs to consider how records were linked and
what the sources could record. Correlation establishes a basis for
diagnosis, but linking two observations does not by itself explain why
the request failed.


\section{Security Telemetry and Derived Features}
\label{sec:background:security-telemetry}

Security Information and Event Management (SIEM) systems bring together
events from sources such as firewalls, intrusion detection systems and
operating system audit logs for analysis. The meaning of these events
depends on the source, its logging policy and the direction of the traffic
\parencite{lee2022sierra}. For example, a firewall denial may reflect an
intended restriction or a configuration mistake that blocks a required
connection. The recorded action alone does not distinguish between them.

Network Detection and Response (NDR) systems focus on potential threats in
network activity. Their alerts provide an interpretation of what was
observed. Research using an NDR deployment examines alerts containing
timestamps, source addresses, destination addresses where available, and
descriptions of the detected activity \parencite{homayoun2024ndrnoise}.
These details help an analyst investigate an alert without treating its
presence as proof of an attack.

\noindent\textbf{Constructing features.} A feature is a property used to
describe an observation for analysis. It can come directly from a record,
such as the protocol, or be calculated from several observations.
\emph{Feature engineering} involves constructing and transforming these
properties into a useful representation. For example, a network flow groups
packets belonging to a connection. Features calculated from it can include
the duration, packet count and time between packets
\parencite{engelen2021troubleshooting}.

Several log entries can be combined into a simple summary. For example,
we could count how many log entries show that a firewall blocked traffic
during five minutes. That count is a \emph{derived feature}. We could also
count how many different source IP addresses appear in those entries.
SIERRA uses counts of events and source addresses over set periods to
analyse security logs \parencite{lee2022sierra}.

The summary helps show how often traffic was blocked. To understand why,
an investigator needs to examine the individual log entries and the
firewall rules.

\noindent\textbf{Interpreting features.} A feature can help a model classify
examples correctly in one dataset while being unrelated to the security
problem. Research on machine learning in security describes how a model
can learn a particular IP address range instead of behaviour associated
with attacks \parencite{arp2022dosdonts}. An address may therefore be useful
for finding related records without being a reliable indicator of
malicious activity.

Errors can also arise before the data reaches a model. A study of the
CICIDS2017 intrusion detection dataset identified problems in flow
construction, feature extraction and labelling
\parencite{engelen2021troubleshooting}. Assessing a feature therefore
requires checking both its relevance to the problem and how it was
calculated from the original observations.


\section{Root-Cause Analysis and Diagnostic Evidence}
\label{sec:background:root-cause-analysis}

A failed request tells an investigator that something went wrong, but it
does not necessarily explain why. A \emph{symptom} is an observable sign
of a problem, such as a timeout or an increased error rate. A \emph{fault}
is the underlying problem that causes a service to fail.
Root-cause analysis (RCA) aims to work back from the observed failure
towards its cause \parencite{li2022circa}. Finding an error message is
therefore a starting point for diagnosis. The next question is what
caused the operation to fail.

Dependencies make this distinction important. If one service waits for
another service to respond, a delay in the second service can also make
the first service appear slow. Research on microservice performance
debugging describes how such delays spread through a request path
\parencite{gan2021sage}. Both services may show a change at the same time,
but this does not mean that both are faulty. Nor is the largest change
necessarily closest to the cause. In its simulation study, CIRCA shows that a
metric associated with the underlying fault can change less noticeably
than metrics affected by that fault \parencite{li2022circa}. An investigation
therefore needs to consider how components affect one another, rather
than simply choosing the most unusual measurement.

An alert can also have more than one possible explanation. Research on
cloud incident diagnosis reports that incidents with the same alert type
can have different causes. The RCACopilot study uses additional diagnostic
information from several sources to investigate those causes
\parencite{chen2024rcacopilot}. This illustrates the role of
\emph{diagnostic evidence}: observations that help assess a particular
explanation for the failure.

\noindent\textbf{Connecting evidence to an explanation.} Consider a
hypothetical application that times out while trying to connect to a
database. The timeout alone does not show whether the database is
unavailable, the application is using the wrong destination, or a firewall
is blocking the connection. Suppose a firewall log can be linked to that
connection and records a denial. Azure Firewall logs can provide the
addresses, ports, protocol and action needed to examine such an event
\parencite{microsoft2026firewallmonitor}. In this example, the denial helps
explain why the connection failed, but further evidence is needed to
understand why the traffic was blocked.

The firewall rule and the application's configuration help distinguish
the remaining explanations. If the application is using the intended
destination and the firewall rule blocks a connection that should be
allowed, the evidence points towards the rule. If the application instead
uses an incorrect destination port, the firewall may be enforcing the
intended policy correctly. The application configuration would then need
attention. These possibilities show why identifying where traffic was
blocked is different from identifying which configuration is wrong.

A clear diagnosis connects the conclusion to these observations. In the
example, it should identify the failed connection, the record showing the
denial and the configuration detail that explains it. This allows another
person to check how the conclusion was reached. It also separates what
was directly observed from what was inferred. The denial is recorded
evidence. Whether it resulted from an incorrect firewall rule remains
an explanation to be assessed against the intended configuration.

The available information may not settle that question. Research on
cloud incident diagnosis describes missing, incomplete and inconsistent
data as practical obstacles to RCA \parencite{chen2024rcacopilot}.
If the intended configuration is unknown in the example, the evidence
supports reporting that the connection was blocked. It does not yet
justify deciding which configuration should change. A useful diagnosis
can therefore state what is known, which explanations remain possible
and what information is needed to distinguish them.


\section{AI Agents and Multi-Agent Systems}
\label{sec:background:agents}

A large language model (LLM) generates text in response to an input,
commonly called a \emph{prompt}. Instructions and examples in that input
can guide how the model approaches a task. Research on GPT-3 demonstrated
that a model could perform different language tasks from instructions or
examples without being retrained for each task
\parencite{brown2020fewshot}. This distinction is useful when interpreting
operational telemetry. Giving a model log entries to analyse supplies
information for its current response. It does not, by itself, train the
model or give it ongoing access to the system that produced the logs.

An LLM-based \emph{agent} places the model within software that can retain
information, select actions and interact with an environment. The CoALA
framework describes these elements through memory, available actions and
a process for choosing what to do next
\parencite{sumers2024coala}. The model is therefore one component of the
agent.

\noindent\textbf{Using tools and observations.} A tool is a function the
agent can use to perform a particular operation, such as retrieving log
entries. The model can select a tool and supply its inputs, while the
surrounding software executes the function and returns the result
\parencite{sumers2024coala}. ReAct describes an approach in which reasoning
and actions alternate. New observations can guide the next action instead
of requiring every step to be decided in advance
\parencite{yao2023react}.

For example, an agent investigating a failed request could first retrieve
application logs for the relevant period. A connection error might lead it
to request firewall records for the affected destination. It could then
compare the returned records or seek more information. This hypothetical
sequence illustrates how tool use supports an investigation. Writing that
a query should be run is different from running it and receiving its
result.

The agent also needs to carry information between these steps. Its
\emph{state} is the information retained during the task, such as the
request being investigated, previous tool results and unresolved questions.
CoALA distinguishes information used in the current decision from
information stored for later retrieval
\parencite{sumers2024coala}. For a telemetry investigation, this distinction
can be illustrated by keeping a short description of the current findings
while retaining the original records separately. A later step could then
inspect a record again instead of relying only on the summary.

\noindent\textbf{Dividing and coordinating the work.} A multi-agent system
allows several agents to contribute to a task. AutoGen describes agents
with different roles and capabilities that exchange messages
\parencite{wu2023autogen}. The agents can use the same underlying language
model while receiving different instructions, tools and conversation
histories. A specialised role therefore does not necessarily require a
separately trained model. It can be established by configuring which part
of the task an agent handles and which tools it can use.

The way this work is organised is called \emph{orchestration}. It
determines which agent acts next, what information it receives and when
the interaction ends. AutoGen supports both predefined interaction
patterns and conversations that change as the task progresses
\parencite{wu2023autogen}. For example, a workflow could pass results
through a fixed sequence of agents. Alternatively, a coordinating agent
could select another agent based on the information still needed.
Programmed conditions can also limit the conversation or request human
input.

In a hypothetical telemetry investigation, one agent could inspect
application errors while another examines firewall events. Their findings
would need to be brought together to explain the same failure. If the
first agent reports a database connection error, the second needs enough
detail to investigate that connection. A message such as \enquote{the
database is unreachable} omits the destination and the time of the failed
attempt. Sharing those details together with the supporting records would
make the handover more useful. This illustrates why assigning separate
roles also creates a need for clear communication.

\noindent\textbf{Limits of agent reasoning.} An LLM can produce a plausible
explanation containing invented or incorrect facts, often called
\emph{hallucination}. Access to external information can reduce this
problem, but it does not ensure a correct answer. The ReAct study reports
failures involving unhelpful search results, incorrect reasoning and
repeated actions \parencite{yao2023react}. In an operational investigation,
a query can execute successfully without providing enough information to
explain a failure. The agent's interpretation of the result still needs
to be checked against the records.

Collaboration introduces further failure possibilities. A study of
multi-agent LLM systems identifies cases where agents fail to share
important information, ignore another agent's input or end a task before
it has been checked properly \parencite{cemri2025mast}. These findings
show why adding agents does not guarantee a better result. For example,
if several agents repeat an incorrect summary from one earlier step,
their agreement supplies no additional evidence for that summary.
Reviewing a diagnosis is useful only if the review can question its
assumptions and examine the evidence behind it.

These limitations connect agent coordination to the diagnostic evidence
discussed in Section~\ref{sec:background:root-cause-analysis}. Dividing the
work can organise access to different sources, but the final explanation
still needs to show how the observations support the proposed cause.


\section{Human-Approved Remediation and Safety Controls}
\label{sec:background:remediation}

Remediation changes a system to address a fault or restore its operation.
An agent that recommends a change therefore needs more than a plausible
diagnosis. The change must also be appropriate for the affected resource,
and its result must be checked. The NIST AI Risk Management Framework
highlights testing, monitoring and the ability to intervene when an AI
system behaves unexpectedly \parencite[pp.~14--15]{tabassi2023airmf}.
For operational agents, these concerns extend from the proposed action
to what happens after it is executed.

\noindent\textbf{Restricting actions.} An \emph{allowlist} specifies which
actions are permitted and rejects actions outside that set. NIST describes
this permit-by-exception approach alongside \emph{least privilege}, which
limits users and processes to the access needed for their tasks
\parencite[AC-6 and CM-7(5)]{nist2020securitycontrols}. For example, a tool
could permit changing one firewall rule while rejecting deletion of the
firewall. The permitted action also needs limits on its target and parameters.

These restrictions need to be enforced by the software executing the
action. Instructions given to the model are not a reliable access-control
mechanism. Research on \emph{indirect prompt injection} demonstrates how
instructions embedded in retrieved content can redirect an LLM
application's behaviour \parencite{greshake2023indirect}. A comparable
risk could arise when a log entry contains text supplied by an external
user. That text belongs to the evidence being examined. It should not
be able to grant permission for an action.

\noindent\textbf{Dry-run validation.} A dry run checks or previews a proposed
change without applying it to the target system. Azure Resource Manager's
\emph{what-if} operation is one example. It predicts changes from a
deployment template, allowing them to be inspected before deployment
\parencite{microsoft2026whatif}. Its output has limits. For example,
Microsoft documents cases where the tool cannot calculate a value used
in the template. It may then report a change even though the final value
stays the same. A preview must therefore be interpreted according to what
the tool can determine. It also does not demonstrate that the application
will recover after the change. An agent's written prediction of success
is not a substitute for this check.

\noindent\textbf{Human approval.} An authorised person reviews a specific
change before execution. NIST's configuration change control guidance
calls for reviewing changes, considering their security impact and
implementing approved changes \parencite[CM-3]{nist2020securitycontrols}.
In a remediation workflow, the proposal needs to identify the target,
the intended change and the evidence supporting it. If that proposal
changes after review, the revised action requires a new approval.

Having a person in the process does not guarantee that an error will be
caught. In a controlled study of AI-assisted decision-making, participants
sometimes accepted incorrect recommendations despite receiving
explanations. Designs that encouraged closer consideration reduced this
overreliance but did not eliminate it \parencite{bucinca2021trust}.
This finding motivates giving the reviewer access to the underlying
evidence and predicted changes. A convincing explanation from the agent
is not sufficient grounds for assuming that the proposed repair is
correct.

\noindent\textbf{Recovery verification.} Completing a configuration update
and restoring a service are different outcomes. A successful management
operation confirms that the change was applied, but the original request
may still fail. Verification therefore examines the resulting behaviour.
Microsoft's deployment guidance recommends monitoring workload health
and considering actual usage when interpreting an absence of errors
\parencite{microsoft2026safedeployments}. For example, a quiet error log
does not demonstrate recovery if no requests have been made. Repeating
the affected operation can provide more direct evidence, alongside checks
for unintended changes to other behaviour.

\noindent\textbf{Rollback.} Rollback undoes a change by restoring an earlier
configuration or version. It requires that the earlier state is available
and that a restoration procedure exists. Microsoft recommends retaining
versioned deployment artefacts and notes that database and other changes
involving stored data can be difficult to reverse
\parencite{microsoft2026safedeployments}. Simply recording an intention to
undo a change does not establish that it can be undone.

Rollback also needs verification. If a firewall rule is restored, its
resulting configuration can be compared with the saved version. The
application's behaviour then needs a separate check. In a failed repair
attempt, restoring the previous configuration may also restore the
original fault. Undoing the attempted repair and resolving the incident
are therefore separate outcomes.

Records of the proposal, approval, action and result make the process
reviewable. NIST's change control guidance includes retaining change
records and monitoring associated activities
\parencite[CM-3]{nist2020securitycontrols}. These records connect the
authorised change to what actually happened.
