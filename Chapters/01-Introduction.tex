\section{Context and Motivation}
\label{sec:introduction:context}

When an application request fails, the cause is not always in the component
where the problem becomes visible. Research on microservice performance
debugging shows how problems in one service can affect other services that
depend on it \parencite{gan2021sage}. An investigation therefore needs to
connect observations from several components to understand where a problem
started and how it affected the request.

This thesis investigates this challenge in collaboration with Norlys. The
selected application request path involves Cloudflare, Azure Firewall,
Azure infrastructure and the application itself. The current troubleshooting
process described by Norlys requires operators to inspect these systems
separately and manually connect timestamps and request identifiers
\parencite[Background]{norlys_operations_agents}. This creates a need to
bring the available evidence together and use it to identify the cause of
a failure.

Shared identifiers can help connect observations across systems. The W3C
Trace Context standard defines a common format for passing trace identifiers
between participating services \parencite{w3c2021tracecontext}. For this
project, it is necessary to examine which identifiers are available and
whether they can link observations along the selected request path.

The content of the telemetry also matters, particularly when investigating
security-related problems. Research on machine learning in security shows
that models can learn patterns that are unrelated to the security problem
they are intended to detect \parencite{arp2022dosdonts}. This motivates
examining which telemetry data and derived features provide relevant
evidence for diagnosis in the selected environment.

Large language model (LLM) agents offer a possible way to coordinate the
investigation. ReAct combines model reasoning with actions that gather
information from external sources \parencite{yao2023react}. AutoGen describes
how agents can work together using different roles, tools and human input
\parencite{wu2023autogen}. These studies provide a basis for investigating
whether specialised agents can gather telemetry from different systems and
combine it into a diagnosis supported by evidence.

Remediation adds another challenge because it involves changing the system.
The NIST AI Risk Management Framework highlights the importance of testing,
monitoring and human intervention \parencite[pp.~14--15]{tabassi2023airmf}.
For this thesis, proposed changes must be checked and approved before they
are carried out. The project will investigate whether the planned controls
help the system resolve faults without making unintended changes.

The aim is to design, implement and evaluate a multi-agent proof of concept
using real operational telemetry. The work will examine how telemetry can
be connected, which data is relevant to security-related diagnosis, and how
well the system diagnoses and remediates faults. A systematic literature
review will inform the research-related parts of the project.

\section{Problem Statement and Research Questions}
\label{sec:introduction:research-questions}

This thesis addresses the following problem statement:

\begin{quote}
How can a multi-agent AI system be designed and evaluated to correlate
telemetry from multiple operational systems and support evidence-based
diagnosis and safe, human-approved remediation of controlled failures in a
non-production Cloudflare-to-Azure application request path?
\end{quote}

The investigation is structured around four research questions:

\begin{description}
    \item[RQ1:] How can a multi-agent system access and correlate telemetry
    from Cloudflare, Azure Firewall, Azure infrastructure, and applications
    to reconstruct the path of a failing endpoint request?

    \item[RQ2:] Which telemetry data and derived features are relevant for
    diagnosing security-related problems along the Cloudflare-to-Azure
    application request path?

    \item[RQ3:] How accurately and consistently can the system identify the
    faulty layer/component and support its diagnosis with relevant evidence
    across different scenarios?

    \item[RQ4:] How safely and effectively can the system plan and execute
    allow-listed remediations under human approval, including dry-run
    validation, recovery verification and rollback?
\end{description}

\section{Scope and Delimitations}
\label{sec:introduction:scope}

Norlys' wider \emph{Centralized Observability Platform Story} specifies a
platform for telemetry ingestion, normalisation, protection of sensitive data,
analysis and remediation. It explicitly states:
\enquote{This is a large cross-cutting story and should be decomposed into
smaller tasks and delivery milestones.}
\parencite[Description]{norlys_observability_spec}
The thesis addresses the focused \emph{Operations with AI Agents} proof of
concept within this wider initiative. Its scope covers investigation across
the four specified telemetry sources and human-approved remediation within
a designated test path. Platform-wide ingestion, normalisation, data
obfuscation and retention remain responsibilities of the parent initiative
\parencite[Scope]{norlys_operations_agents}.

Within this test path, remediation is limited to allow-listed actions.
The planned workflow includes dry-run validation, human approval, recovery
verification and rollback \parencite[AC-5]{norlys_operations_agents}.

The security-related investigation concerns telemetry and derived features
associated with the same request path. The findings will be interpreted in
relation to the available data, the selected environment and the scenarios
examined. These boundaries also frame the assessment of diagnostic
effectiveness and remediation safety.
